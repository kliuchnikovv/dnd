# M1a — консольный детективный прототип. Дизайн

Дата: 2026-08-18
Модуль: `github.com/kliuchnikovv/dnd`
Статус: согласован, готов к плану реализации

## 1. Цель и критерий остановки

Консольный прототип детективной игры без единого вызова LLM. Одно рукописное
дело грузится из JSON. Прототип отвечает на один вопрос: **ощущается ли
текстовое расследование игрой.** Отрицательный ответ останавливает проект здесь.

Побочный, но постоянный результат: харнесс для отладки и eval-прогонов. Поэтому
воспроизводимость закладывается с первого коммита, а не достраивается потом.

## 2. Границы

**Есть:** ядро, система правил «Порог», одно рукописное дело, CLI, тесты.

**Нет намеренно:** LLM, естественный язык, генератор дел, валидатор генерации,
спящие пути и щиты, веб, парти и кооп, регионы, ассеты, модерация, биллинг,
дневники сущностей, ночная смена. Рукописное дело разрешимо по построению,
поэтому машинерия надёжности переносится в M1b.

**Нет проигрышного состояния.** Часы, заполнившись, меняют мир, но не убивают
прогон. Прототип измеряет вовлечённость, а не фрустрацию.

## 3. Решения, принятые на брифе

| Вопрос | Решение |
|---|---|
| Кто пишет дело | Дело целиком пишет исполнитель: сущности, граф фактов, `truth`, настоящий флейвор-текст |
| Глубина боёвки | Все боевые глаголы резольвятся и покрыты тестами; рукописное дело их не требует, прохождение чисто детективное |
| Детерминизм | `--seed N` + скриптовый ввод. Журнала событий и снепшотов в M1a нет |
| Архитектура | Подход A: раздельные пакеты `core` / `rules`, шов через интерфейс |

## 4. Структура пакетов

```
core/      граф фактов, держатели, разблокировки, party_knowledge,
           корроборация, часы, форма обвинения, таксономия цены провала,
           RNG с именованными стримами, типы Intent/SceneView/Resolution/Mutation
rules/     threshold: лист персонажа, ситуативные модификаторы, выбор порога,
           Resolve, grit, словарь глаголов и их применимость
store/     «таблицы» — map[ID]Row, колонка в колонку с будущей схемой Postgres
cases/     загрузчик JSON дела + валидатор инвариантов
cli/       парсер команд, рендер сцены, REPL и скриптовый режим
cmd/dnd/   main
```

Зависимости направлены в одну сторону: `cli → core → store`, `cli → rules`,
`rules → core` (только за типами границы). **`core` не импортирует `rules`.**

## 5. Шов «ядро / система правил»

### 5.1 Интерфейс

```go
// объявлен в core
type RuleSystem interface {
    Resolve(Intent, SceneView, Dice) Resolution
}
```

Ядро передаёт `(Intent, SceneView, Dice)` и получает `Resolution`. Ядро никогда
не видит кости: значение броска существует только внутри `Resolve` и в
человекочитаемом `Resolution.Log`.

### 5.2 Типы границы

```go
type Intent struct {
    Verb  Verb      // один из перечисленных в §8
    Actor EntityID
    Args  Args      // target?, topic?, node?, facts?, item?, ability?, tag_claim?
}

type SceneView struct {
    Node         NodeID
    NodeTags     []string   // теги обстановки: dark, crowd, rain, indoors, ...
    Allies, Foes int        // численность в зоне
    Undetected   bool
    Cover        bool
    TargetTier   int
    ActorTier    int
    Tools        []string
    Harm         int        // заполненные ячейки ранений
    Grit         int
    Sheet        json.RawMessage // лист персонажа, непрозрачен для ядра
}

type Resolution struct {
    Class     Outcome     // Crit | Success | Partial | Fail
    Margin    int
    Costs     []CostKind  // выбраны правилами из таксономии ядра
    Mutations []Mutation
    Log       RollLog     // d20 и именованные слагаемые, для вывода игроку
}

type Mutation struct {
    Kind   MutationKind // Resource | Clock | Harm | Disposition | Position
    Target string       // имя ресурса/часов/сущности — даёт система правил
    Delta  int
}
```

**В `SceneView` нет графа фактов и нет `cases.truth`.** Система правил
физически не может их прочитать. Что именно узнала парти при успехе — решает
ядро по `fact_holders.gate` и классу исхода.

**`Sheet` непрозрачен для ядра.** Ядро хранит `characters(id, sheet, harm[],
grit)`: `harm` и `grit` — известные ядру счётчики, потому что таксономия цены
провала на них ссылается; всё остальное содержимое листа — байты, которые ядро
передаёт правилам не разбирая.

### 5.3 Поток одного хода

`core.Apply(intent) → Outcome` выполняет ровно пять шагов:

1. **Валидация.** Тема есть в `party_knowledge`? Узел достижим? Цель в сцене?
   Глагол применим к цели? Отказ — не провал: ход не тратится, часы не тикают.
2. **Ветка без броска.** `mandatory`-факт при нужном узле выдаётся сразу,
   `Resolve` не вызывается. Сюда же `compare` — противоречие есть либо нет.
3. **Сборка `SceneView`.**
4. **`rules.Resolve(intent, view, dice)`** — чистая функция.
5. **Применение.** Ядро выбирает открывшийся факт, пишет строку в
   `party_knowledge` с источником, применяет `Mutations`, исполняет `Costs`.

### 5.4 Таксономия цены провала

Закрытый enum ядра:

```
TickClock | FalseLead | Debt | DispositionDown | PositionWorse |
HarmSelf | ResourceSpent | HalfEffect
```

Правила **выбирают** элементы по классу глагола и удваивают список при
марже ≤ −10. Ядро **исполняет**. Ни одна сторона не делает обе вещи.

### 5.5 Проверка шва

Механически, в CI:

- `go list -deps ./core` не содержит `./rules`
- grep по `core/` на `d20`, `math/rand`, `grit +`, названия атрибутов — пуст

## 6. Модель данных

Таблицы повторяют будущую схему Postgres. Ссылки — по id, **без указателей
между сущностями**: переезд в Postgres должен быть механическим `INSERT`, а не
переписыванием обхода.

```
facts            (id, case_id, key, kind)              kind: concept | transition
fact_holders     (fact_id, holder_id, gate, mandatory, latent)
fact_unlocks     (fact_id, unlocks_kind, unlocks_id)
entities         (id, name, kind, voice)               kind: npc | record | thing
locations        (id, name, adjacent[])
relations        (from_entity, to_entity, kind)
cases            (id, archetype, truth, status)
party_knowledge  (fact_id, learned_from_entity, confidence, learned_at)
clocks           (id, name, segments, filled, tick_policy)
characters       (id, sheet, harm[], grit)
```

`party_knowledge` ключуется парой `(fact_id, learned_from_entity)`: два
свидетельства — две строки. Это основа корроборации.

### 6.1 Семантика трёх полей `fact_holders`

**`gate`** — условие выдачи, не число:

```json
{ "verbs": ["question", "examine"], "threshold": "normal", "requires": ["fact_id"] }
```

Глагол не из списка факт не выдаёт. `requires` — предпосылки; без них держатель
молчит.

**`mandatory`** — держатель отдаёт факт без броска. Инвариант дела: **у каждого
факта есть хотя бы один mandatory-держатель.** Единственная защита от «кубик
убил дело».

**`latent`** — факт у держателя есть, но темы для него нет в банке, пока
`fact_unlocks` его не откроет. Это то, что превращает набор проверок в
расследование.

### 6.2 Изоляция `truth`

`cases.truth` не попадает ни в один вывод — и это гарантируется типом, а не
дисциплиной:

```go
type Truth struct { who, how, when, why FactID } // поля приватные

func (Truth) String() string               { return "<redacted>" }
func (Truth) MarshalJSON() ([]byte, error) { return nil, ErrTruthNotSerializable }
```

Единственный доступ — `accusation.Check(form) bool`, возвращающий один булев.

### 6.3 Формат дела

Один JSON: `entities`, `locations`, `facts`, `fact_holders`, `fact_unlocks`,
`relations`, `clocks`, `truth`, `flavour`.

`flavour` — словарь `key → текст`: сцены локаций, реплики держателей по факту,
ответы «не знаю», описания последствий часов. **Код никогда не конкатенирует
текст, только достаёт по ключу.** Флейвор пишет автор дела; заглушки дадут
ложный негатив на главном вопросе, поэтому текст пишется настоящим.

### 6.4 Валидатор загрузки

Падает при старте, а не на сороковой минуте игры:

- каждый слот `truth` достижим из стартового состояния
- у каждого факта есть mandatory-держатель
- каждый truth-факт имеет ≥ 3 попарно независимых источника
- все ключи `flavour`, на которые ссылаются данные, существуют
- `adjacent` симметричен, все id разрешаются

## 7. Правила «Порога»

### 7.1 Резолюция

```
Итог  = d20 + Атрибут + Тег + Ситуативные
Маржа = Итог − Порог

Маржа ≥ +5   → КРИТ
Маржа  0…+4  → УСПЕХ
Маржа −1…−4  → ЧАСТИЧНО
Маржа ≤ −5   → ПРОВАЛ

нат-20 → класс на ступень вверх
нат-1  → класс на ступень вниз
```

Порог — закрытое множество: `Легко 10`, `Норма 14`, `Трудно 18`. Назначается
функцией от состояния: «Норма» по умолчанию, «Легко» при преимуществе обстановки
или инструмента, «Трудно» при активном противодействии.

### 7.2 Лист персонажа

- 4 атрибута `body`, `edge`, `mind`, `will`; сумма на старте 4, максимум +3 в одном
- 2 тега, +2 к броску; **применимость — по списку** глаголов и тегов обстановки,
  не по смыслу
- 3 ячейки ранений, −2 за ячейку, на третьей персонаж выведен из строя
- `grit 3` — единственный push-ресурс: 1 очко даёт +2 до броска либо
  конвертирует выпавший Провал в Частично
- 4 архетипа по 3 способности

В M1a персонаж предгенерирован в деле; экрана создания нет.

### 7.3 Ситуативные модификаторы

Сумма в пределах ±4, вычисляется, не оценивается:

| Фактор | Значение |
|---|---|
| Численное превосходство в зоне | ±2 |
| Укрытие или высота | +2 |
| Не обнаружен | +2 |
| Темнота, дождь, толпа | −2 |
| Ранения | −2 за ячейку |
| Разница Tier с целью | ±2 |
| Подходящий инструмент | +2 |

Ни одного «на усмотрение мастера»: `Resolve` — чистая функция от
`(Intent, SceneView, Dice)`.

### 7.4 Выбор цены провала

| Класс | Частично | Провал |
|---|---|---|
| investigate | получил + `TickClock` | `FalseLead` либо `TickClock` |
| reason | — | — |
| social | получил + `Debt` | `TickClock` + `DispositionDown` |
| move | попал + `PositionWorse` | остался + `TickClock` |
| attack | урон цели + `TickClock` | `HarmSelf` либо `PositionWorse` |
| support | `HalfEffect` | `HarmSelf` |
| resource | эффект + `ResourceSpent` | `ResourceSpent` без эффекта |
| skill | получил + `PositionWorse` | `TickClock` + `PositionWorse` |

Маржа ≤ −10 → список цены удваивается.

### 7.5 Отдых

Короткий: восстанавливает `grit`. Длинный: снимает ячейку ранений **ценой тика
часов, который предъявляется игроку до отдыха**. Длинный отдых — структурный
переход, а не арифметика игровых часов.

## 8. Глаголы

Аргументы однородны: `{target?, topic?, node?, facts?, item?, ability?, tag_claim?}`.

| Уровень | Глаголы | Класс | Бросок |
|---|---|---|---|
| Flavour | `look`, `emote`, `say` | — | нет |
| Soft | `talk_to`, `ask_about`, `thank`, `threaten_verbally` | social | нет |
| Soft | `theorize` | reason | нет |
| Hard | `examine`, `search`, `question`, `stake_out`, `tail` | investigate | да |
| Hard | `compare` | reason | **нет** |
| Hard | `cross_reference` | reason | да |
| Hard | `strike`, `grapple` | attack | да |
| Hard | `move_zone`, `take_cover`, `flee` | move | да, кроме безопасных |
| Hard | `sneak`, `pick`, `recall` | skill | да |
| Hard | `persuade`, `intimidate`, `command` | social | да |
| Hard | `aid`, `mend` | support | да |
| Hard | `use_ability`, `use_item` | resource | по флагу в определении |

Итого **30** глаголов. См. §12 о расхождении с числом «26» в брифе.

Три правила:

1. **Банк тем строится из `party_knowledge`.** Спросить о факте, которого парти
   не знает, нельзя. Это защита от угадывания, а не ограничение.
2. **`compare` без броска.** Противоречие между двумя известными фактами — это
   свойство данных, а не удача. Игрок сопоставил — игрок заметил.
3. **`mandatory`-факт выдаётся без броска**, если парти в нужном узле и действие
   осмысленно.

## 9. Обвинение, корроборация, часы

**Обвинение.** Слоты `who / how / when / why`; токен доступен только под
собранный факт. Проверка символьная и целиком: либо все четыре верны, либо «есть
ошибки» — **без указания слота**. Попытка стоит тик часов, иначе слоты
брутфорсятся по одному. Счётчик попыток виден игроку.

**Корроборация.** Источники факта обходятся в хронологическом порядке; источник
засчитывается, если в `relations` нет ребра ни с одним уже засчитанным. Затем
`1 − Π(1 − pᵢ)` при `p = 0.5`: один источник — 0.5, два — 0.75, три — 0.875.
Порог действенности 0.8, то есть нужно три независимых источника. Обход
детерминированный; перебора независимых множеств нет.

**Часы.** Заполнение — не проигрыш, а срабатывание последствия из дела:
свидетель уезжает, улика исчезает, держатель переходит в `hostile`. Инвариант
разрешимости сохраняется: mandatory-путь к каждому факту остаётся.

## 10. CLI

```
question <источник> <тема>        расспросить
examine <предмет>                 осмотреть
search <локация>                  обыскать
compare <факт> <факт>             сопоставить
cross_reference <факт> <запись>   сверить
stake_out <локация>               наблюдать
theorize <текст>                  зафиксировать гипотезу
accuse                            открыть форму обвинения
facts                             известные факты с источниками и confidence
state                             узел, часы, ранения, grit, попытки
clocks                            часы давления
help
```

Ввод структурированный, не естественный язык: `question ivar ledger`.

**Отказ ≠ провал.** Неизвестный глагол, неизвестная тема, недостижимый узел →
сообщение об отказе с подсказкой; ход не потрачен, часы не тикнули. Игрок должен
видеть разницу мгновенно, иначе решит, что игра сломана.

`facts` печатает факт, список источников и `confidence` — единственный интерфейс
к корроборации, и по нему видно, зачем нужен третий свидетель.

Вывод сцены берётся из флейвора дела по ключу.

### 10.1 Детерминизм

```
dnd --case case.json --seed 7                   интерактивный REPL
dnd --case case.json --seed 7 --script run.txt  скриптовый прогон
```

RNG — именованные стримы: `resolve`, `false_lead`, `flavour`, каждый со своим
PRNG от `hash(seed, name)`. Добавление броска в одном месте не сдвигает
последовательность в другом — иначе `--seed` перестаёт воспроизводить прогон
после любой правки. Пара `(seed, скрипт)` полностью задаёт вывод; баг-репорт —
два файла.

## 11. Тесты

Порядок работы — TDD. Тест распределения исходов и тест разрешимости пишутся до
движка: оба формулируются раньше, чем существует код.

| Тест | Как |
|---|---|
| Распределение исходов | **Точный перебор** 20 граней, не сэмплирование: при +4/Норма ровно 11/20 успех+, 4/20 частично, 5/20 провал, с учётом сдвигов от нат-20 и нат-1. Ни одного флакающего теста |
| Каждый глагол резолвится | table-driven по всем 30, ни одного `default: panic` |
| Каждая цена применяется | 8 классов × {Частично, Провал}, плюс удвоение при марже ≤ −10 |
| mandatory сильнее кубика | `Dice`, всегда возвращающий 1 — дело всё равно проходимо |
| Достижимость | 200 прогонов случайного агента, seed 0..199: форма обвинения собираема в каждом |
| Корроборация | связанные источники не дают 0.875 |
| Обвинение не брутфорсится | 3 верных слота и 0 верных дают побайтово одинаковый вывод |
| Шов | `go list -deps ./core` не содержит `./rules` |
| Ни одного LLM | grep по репозиторию: нет сетевых импортов и вызовов моделей |

Целевое распределение для теста:

| Модификатор | Порог | Успех+ | Частично | Чистый провал |
|---|---|---|---|---|
| +4 | Норма | 55% | 20% | 25% |
| +6 | Норма | 65% | 20% | 15% |
| +4 | Трудно | 35% | 20% | 45% |

«Частично» держится на 20% почти при любом модификаторе — следствие
фиксированного окна маржи в 4 пункта. Доля fail-forward не зависит от прокачки,
и это фича.

## 12. Расхождения брифа и как они закрыты

**Число глаголов.** Бриф заявляет 26 (18 базовых + 8 детективных), но
перечисляет 30. Детективных ровно 8 (`examine`, `search`, `question`,
`stake_out`, `tail`, `compare`, `cross_reference`, `theorize`), базовых
получается 22. **Источник истины — перечисление, а не число.** Реализуются все
30; тест «каждый глагол резолвится» перебирает список, а не константу.

**Класс `skill` отсутствует в таксономии цены провала.** Бриф даёт 7 строк
(investigate, reason, social, move, attack, support, resource), но `sneak`,
`pick`, `recall` имеют класс `skill`. Восьмая строка добавлена в §7.4:
Частично → получил + `PositionWorse`; Провал → `TickClock` + `PositionWorse`.
Логика — провалившаяся скрытность стоит позиции и времени, но не крови.

**`use_ability` / `use_item` — «бросок: зависит».** Разрешено флагом
`requires_roll` в определении способности или предмета в данных дела, а не
эвристикой в коде.

**Поведение заполненных часов брифом не задано.** Решение в §9: последствие из
дела, не проигрыш.

## 13. Definition of done

- Рукописное дело проходится от первой сцены до верного обвинения только через CLI
- Скрипт `walkthrough.txt`, проходящий дело до верного обвинения, лежит в
  репозитории и гоняется в тестах: сломанное правкой дело роняет CI
- Все тесты §11 зелёные
- Ни одного вызова LLM в коде
