# Капабилити-таблица ролей. Дизайн

Дата: 2026-08-21
Модуль: `github.com/kliuchnikovv/dnd`
Статус: согласован, готов к плану
Основание: `docs/adr/0001-layered-world-trusted-core.md` (сердцевина варианта А)

## 1. Повод

ADR-0001 постановил: **LLM предлагают, ядро располагает**, и у каждой роли —
свои полномочия. Сейчас это выражено одной булевой функцией `Role.MutatesState()`,
захардкоженной под единственный `intent_parser`, плюс неявными правилами: актёр
читает `party_knowledge`, нарратор — флейвор, и так далее — но нигде это не
записано и не проверяется. Растёт число ролей (нарратор, куратор окружения,
воркер мира), и «кто что вправе читать и предлагать» должно стать **явным
реестром**, а не устной договорённостью. Иначе новая роль легко получит лишнее
чтение (утечка) или лишнее право (обход ядра).

## 2. Решение

Ввести в `llm/` **реестр капабилити на роль**: что роль **читает**
(least-privilege), что она **предлагает** ядру, и — как инвариант — что **ни одна
LLM-роль не мутирует напрямую**. `RequiresStrictOutput` перестаёт быть
захардкоженным и **выводится** из реестра. Реестр — единственная правда о
полномочиях; роутер и тесты границы его исполняют.

Две оси капабилити:

- **Read scope** — закрытый набор доменов чтения. Того, чего нет в scope роли,
  она не получает в промпт. Среди scope’ов **нет `Truth`** и нет «все холдеры»:
  правда дела и гейтнутые чужие факты недоступны никому из LLM by-design (тип
  `truth` уже несериализуем — реестр делает это правилом для всех ролей).
- **Proposal kind** — что роль вправе предложить ядру. Мутацию роль не применяет
  — она её **предлагает**, ядро валидирует и применяет. Поле «мутирует» у
  LLM-ролей отсутствует конструктивно.

## 3. Таблица (контракт)

| Роль | Читает | Предлагает | Strict out |
|---|---|---|---|
| `intent_parser` | сцена, `party_knowledge`, носимый инвентарь | **команда** (действие игрока) | да |
| `narrator` (Мастер) | авторский флейвор, сцена, канон мира, механический исход (ключ факта, цена) | **канон-ambient** (расширение мира по запросу) | да |
| `actor` | `party_knowledge`, своё досье (голос/желания/нити), гранты Мастера, сцена | ничего (текст + `needs`) | нет |
| `canon_guard` | проверяемая реплика + разрешённый ей материал | ничего (вердикт-совет) | нет |
| `moderation` | ввод/вывод под проверку | ничего (вердикт-совет) | нет |
| `environment_curator` (`worldsmith`) | канон мира, сцена (не-каноничный слой) | **канон-ambient / мир** | да |
| воркер мира | состояние мира | **мутация мира** | да |

Не читает **никто**: `cases.truth`, гейтнутые факты, которых парти не знает.
Не мутирует напрямую **никто из LLM**: только ядро применяет.

`RequiresStrictOutput` = роль что-то предлагает (`Proposes != nothing`).
Почему: предложение, которое ядро применит к состоянию, разобранное из
«почти валидного» JSON, мутирует канон. Совет (guard, moderation) и просто текст
(реплика актёра) строгого провайдера не требуют — плохой парс там даёт бледную
реплику, а не порчу состояния. Это ровно нынешняя логика `MutatesState`, только
выведенная из таблицы и распространённая на нарратора и куратора.

## 4. Что становится строже, и это правильно

Сегодня строгий провайдер требуется только `intent_parser`. По таблице его
начинают требовать и **нарратор с куратором** — как только они получают право
предлагать канон. Это не регресс, а закрытие дыры: канон-мутация из
misparsed-JSON опаснее плохой реплики. Пока путь `needs → grants → мутация` не
построен (это работа под API мутаций ядра), нарратор/куратор предлагают канон
«вхолостую» — реестр объявлен, а enforcement их строгости включается вместе с
API. Для существующих ролей поведение не меняется.

## 5. Что проверяется машинно уже сейчас

- **Полнота.** У каждой объявленной `Role` есть запись в реестре; нет записей на
  несуществующие роли. Забытая роль — провал теста, а не тихая дыра.
- **Вывод строгости.** `RequiresStrictOutput(role)` совпадает с тем, по чему
  фильтрует роутер. Роутер начинает фильтровать по капабилити, а не по
  захардкоженному `MutatesState`.
- **Нет `Truth` в scope.** Ни одна запись не содержит запретного домена чтения
  (такого константа-scope просто не существует; тест стережёт, что не завели).
- **Никто из LLM не мутирует.** У структуры капабилити нет поля прямой мутации;
  тест границы фиксирует, что применяет состояние только ядро (заготовка под
  будущий API мутаций).

Runtime-enforcement самого read-scope (роль физически не может прочитать вне
scope) требует провести все чтения через скоуп-аксессор — это отдельная работа,
она приходит с API мутаций и снепшотом окружения. Здесь scope — **контракт и
проверяемые негативные инварианты**, а вызывающие (актёр/нарратор/парсер)
приводятся к чтению строго из аксессоров своего scope.

## 6. Инварианты

1. Реестр — единственная правда о полномочиях; `MutatesState`/`RequiresStrictOutput`
   выводятся из него, не задаются отдельно.
2. Ни у одной LLM-роли нет права прямой мутации; мутация — предложение ядру.
3. `Truth` и чужие гейтнутые факты вне scope любой роли.
4. Граница домена цела: реестр живёт в `llm/`, домен его не импортирует;
   `architecture_test` зелёный.
5. Поведение существующих ролей (`intent_parser`, `actor`, `canon_guard`) не
   меняется — только формализуется.

## 7. Границы

Есть: реестр капабилити (read scope + proposal kind), вывод `RequiresStrictOutput`,
фильтр роутера по реестру, тесты полноты и границы, приведение существующих
вызывающих к чтению по scope.

Нет намеренно (приходит с API мутаций ядра): runtime-enforcement read-scope через
аксессоры; рабочие пути предложения канона нарратором/куратором; воркер мира;
сам закрытый набор типов мутаций.
