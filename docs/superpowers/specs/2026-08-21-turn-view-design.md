# Протокол turn-view. Дизайн

Дата: 2026-08-21 (ред. 2 — две оси пластичности + surfacing)
Модуль: `github.com/kliuchnikovv/dnd`
Статус: согласован, готов к плану
Основание: `docs/adr/0004-client-and-turn-view.md` (action item №1); принцип двух осей — см. ADR о пластичности правило×сценарий.

## 1. Повод

Клиент (RN) и мультиплеер висят на одном контракте: что сервер отдаёт на ход. Сервера ещё нет, но контракт нужен — и вводится так, чтобы консоль его дожфудила: `turn-view` — Go-структура, которую текущий рендер уже заполняет и печатает, а сервер потом сериализует в JSON без изменения формы.

Два требования, которые формируют вид:

* **Две оси пластичности.** Клиент не завязан ни на набор правил (D&D/«Порог» — одна реализация `RuleSystem`), ни на сценарий (детектив — один архетип). Клиент рендерит дескрипторы; чем они наполнены и как названы — говорит сервер по паре (правило × сценарий). D&D-детектив — референс-конфигурация, не вшитый код.
* **Минимализм через surfacing.** По умолчанию видно только повествование, уместные аффордансы и ввод. Меры и панели всплывают, только когда нужны сейчас, и решает это сервер флагом в виде, а не эвристика клиента.

## 2. Структура (дескрипторы, не конкретика)

```
TurnView {
  Version   int
  Scene     { Node, Title string; ArtRef string }
  Narration []Block                         // проза мастера и реплики NPC (стрим)
  Resolution *Resolution                     // исход броска, если был
  Meters    []Meter                          // состояние: от ПРАВИЛА, что показать — по Surface
  Options   []Option                          // аффордансы = ходы, привязанные к интенту
  Objective *Panel                            // цель/рабочее пространство: от СЦЕНАРИЯ
  Map       *MapView
  Participants []Who
  Ended     *Ending                           // условие победы — сценарное
}

// От ПРАВИЛА — клиент не знает слов «grit»/«раны»/«d20»
Meter  { Label string; Kind string; Value int; Max *int; Surface bool }
Resolution { Terms []Term; Target int; Margin int; Outcome { Label string; Tier string } }
Term   { Label string; Value int }

// Общее ядро — безразлично к обеим осям
Block  { Kind "gm"|"npc"; Text string; Speaker *Who; Streaming bool }
Option { ID, Label, Token string; Check string; Reply bool }   // Check — класс словами, не порог
Who    { ID, Name, AvatarRef string; Disposition int }
MapView{ ArtRef string; Nodes []MapNode }
MapNode{ ID, Name string; Reachable, Known bool; X, Y int }

// От СЦЕНАРИЯ — обобщённая панель; детективное досье это её экземпляр
Panel  { Kind string; Title string; Sections []Section; Surface bool }
Section{ Label string; Items []PanelItem; Slots []Slot }
PanelItem { ID, Label, Sub string; Token string }              // факт+источник+confidence и т.п.
Slot   { Name, Label string; Filled *PanelItem; Options []PanelItem } // who/how/when/why и аналоги
```

* **Meters — от правила.** `grit`, `раны`, `часы`, `heat` подземелья — всё меры, которые правило называет само. `Surface` решает сервер: ранен — раны всплыли, часы близки — всплыли, иначе скрыты. Клиент рисует только `Surface:true`.
* **Resolution — от правила.** d20-«Порог» это `Terms`+`Target`+`Outcome`; клиент рисует термы и исход, не зная про d20.
* **Objective (Panel) — от сценария.** Детективное досье (факты с источниками и confidence в `Sections`, слоты who/how/when/why в `Slots`) — экземпляр архетипа «дедукция». Подземелье пришлёт другую панель. Клиент рендерит обобщённую панель, не «casebook». `Surface` — скрыта по умолчанию, вызывается жестом.
* **Option** переиспользует `core.Affordance`; интент — непрозрачный `Token`, клиент шлёт его обратно, сервер разворачивает и валидирует.
* **Ended** — условие победы сценарное (раскрыл дело / зачистил / ушёл с добычей).

## 3. Где живёт

Пакет `view` над доменом: собирает `TurnView` из состояния ядра (меры, резолюция), правила (метки мер, форма резолюции) и сценария (панель цели) + прозы Мастера. `core` его не импортирует — граница цела. JSON-теги: та же форма — тело ответа сервера.

## 4. Дожфуд консолью

`cli/render.go` переводится на печать из `TurnView`. Печатается только то, что `Surface:true` — минимализм проверяется уже в консоли. Если консоль полна из вида — вид полон и для клиента.

## 5. Инварианты

1. **Обе оси — дескрипторами.** Ни «grit», ни «casebook», ни «d20» в структуре нет как понятий: меры/резолюция от правила, панель от сценария. D&D-детектив — конфигурация, наполняющая дескрипторы, не форма вида.
2. **Шов держится тестом.** Как `architecture_test` бережёт границу домена, так тест бережёт, что вид не знает конкретных правил/сценария (нет захардкоженных меток, панель обобщённая). Строим одну пару, шов честный.
3. **Surfacing — свойство протокола.** Что показать сейчас, решает сервер (`Surface`), не клиент. Минимализм в контракте, а не в пожелании дизайнеру.
4. **Нет утечки.** Ни `truth`, ни гейтнутого-неизвестного факта; `Options` и `Objective` — из read-scope.
5. **Проза — контент, не разметка;** интент валидирует сервер; детерминизм (меры/резолюция/опции — часть правды `(seed, script)`, стрим-проза вне её).
6. **Граница домена:** `view` над `core`; сериализуемо; `core` чист.

## 6. Границы

Есть: `TurnView` из дескрипторов обеих осей, surfacing-флаги, сборка из ядра/правила/сценария, перевод консоли на печать из вида, токены-опции, шов-тест на агностичность + leak-тест.

Нет намеренно: сам сервер/транспорт/стрим/пуш (следующая спека); реальные ассеты (id-заглушки); клиентский RN-рендер; второе правило или сценарий (строим D&D×детектив за честным швом, не N реализаций сразу).
