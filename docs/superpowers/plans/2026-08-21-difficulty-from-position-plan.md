## Инварианты (во всех фазах)

1. `DifficultyFor` — чистая функция, детерминизм как у `Situational`.
2. Ни один вход не приходит от LLM-нарратора; `Opposed`/`Exposed` ставит ядро.
3. Авторский `gate.threshold` сильнее: судимое им действие не меняется.
   `e2e/*`, распределение исходов и достижимость — зелёные.
4. Граница домена: код в `rules/threshold`, `core` его не импортирует.
   `e2e/architecture_test.go` зелёный.
5. `go test ./...` зелёный после каждой фазы.

## Фаза 1 — Сигналы позиции в SceneView

Цель: у ядра есть чем судить, без участия текста модели.

Тронуть:
- `core/scene.go` (тип `SceneView`): добавить `Opposed bool` (цель активно
  мешает действию) и `Exposed bool` (цель открыта/беспомощна). Прокомментировать
  «ставит ядро из состояния, не нарратор».
- `core/…` где собирается `SceneView` (`Game.SceneView`): заполнять новые поля из
  состояния. В M1a детективном бою нет → оба обычно `false`; выставить там, где
  состояние их явно даёт (напр. `Exposed` при связанном/оглушённом — пока может
  быть заглушено `false`, важно завести канал).

Тесты: `SceneView` несёт новые поля; сборка их проставляет из состояния
детерминированно.

## Фаза 2 — Функция сложности

Цель: порог от позиции для несудимого действия; авторский гейт сильнее.

Тронуть `rules/threshold/`:
- `mods.go` (или новый `difficulty.go`): `DifficultyFor(in core.Intent, view
  core.SceneView) string` → `"easy"|"normal"|"hard"`:
  - если `view.GateThreshold != ""` → вернуть его (авторский сильнее);
  - иначе база `"normal"`; ступень к `"hard"` при `view.Opposed` (или adverse
    без инструмента); ступень к `"easy"` при `view.Exposed` (или явный рычаг без
    `Opposed`); **не больше одной ступени**.
- `resolve.go` `Resolve`: заменить `th := ThresholdFor(view.GateThreshold)` на
  `th := ThresholdFor(DifficultyFor(in, view))`. Поведение при заданном гейте не
  меняется (функция вернёт тот же гейт).

Тесты (table-driven, точный разбор как в тесте факторов):
- гейт задан → порог равен гейту при любых `Opposed/Exposed`;
- гейта нет, нейтрально → Норма;
- гейта нет, `Opposed` → Трудно; `Exposed` → Легко;
- одновременно `Opposed`+`Exposed` → не выходит за одну ступень (решить
  приоритет: противодействие перевешивает — вернуть Норма или Трудно, зафиксировать
  тестом);
- распределение исходов из §11 исходной спеки остаётся прежним для судимых
  гейтом действий.

## Фаза 3 — Тест частоты порога

Цель: поймать неверно назначенный порог до игры, не после.

Тронуть:
- `rules/threshold/…_test.go`: на наборе типовых `SceneView` печатать долю
  Легко/Норма/Трудно для несудимых действий. Порог, дающий Трудно (или Легко)
  почти всегда, — ошибка; тест падает при перекосе выше порога (в духе теста
  факторов). Числа — метрика, не «на глаз».

---

## Фаза 4 — Граница с парсером (подсказка класса для импровизации)

Цель: несудимое/импровизированное действие доходит до броска, но порог всё равно
ставит ядро.

Тронуть:
- `intent/…`: если свободный текст не ложится на глагол, но описывает физическое
  действие, парсер вправе **предложить класс** (`attack`/`skill`/`move`/…) как
  подсказку о форме — недоверенную. (Минимально: расширить `reply`/валидацию
  каналом «импровизация + предложенный класс».)
- `core/turn.go`: принять предложенный класс как форму, но **порог и легальность
  решать ядром** (`DifficultyFor`), не парсером. Полная модель реестра
  импровизированных глаголов — отдельный дизайн; здесь только канал + судейство.

Тесты: импровизированное действие получает порог от `DifficultyFor`, а не от
подсказки парсера; подсказка класса не влияет на порог.

## Фаза 5 — Проверка на катке

Сыграть `--nl` короткий бой/сцену: убедиться, что удар по открытой цели ощутимо
легче, по сопротивляющейся — тяжелее, и что порог не зависит от формулировок
игрока или прозы Мастера — только от позиции.
