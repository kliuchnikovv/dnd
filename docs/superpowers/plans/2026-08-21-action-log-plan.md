## Инварианты (во всех фазах)

1. Ядро остаётся чистым: `core`/`rules`/`store`/`cases`/`dice` не импортируют
   журнал; детерминизм ядра не тронут. `e2e/architecture_test.go` зелёный.
2. Правда реплея — структурный интент, не сырой текст; сырой ввод/вывод LLM —
   только в аудите.
3. `(seed, script)` продолжает работать; walkthrough/reachability зелёные.
4. `go test ./...` зелёный после каждой фазы.

## Фаза 1 — Схема журнала (данные, форма под Postgres)

Тронуть `store/`:
- `CommandLogEntry{ SessionID, Seq, SnapshotID, CoreVersion, Intent (структурно
  — переиспользовать сериализуемую форму `core.Intent`/`Args`), DiceCtx{Seed,
  Turn}, IdempotencyKey, Status }`; `Status` = `pending|applied`.
- `AuditEntry{ SessionID, Seq, RawInput, LLMRole, LLMProposal, CoreVerdict }`.
- Append-only «таблицы» в `store.DB` (слайсы/map под Postgres-форму) + методы
  `AppendCommand`, `MarkApplied`, `AppendAudit`, `PendingTail`.

Тесты: append + чтение в порядке `Seq`; `MarkApplied` меняет статус; `PendingTail`
возвращает незавершённое.

## Фаза 2 — Запись до обработки в цикле хода

Тронуть `cli/` (оркестратор; ядро не трогаем):
- Обернуть применение интента (`applyIntentWithHint` → `Game.Apply`): перед
  `Apply` — `AppendCommand(status=pending)` с интентом, `DiceCtx{seed, turn}`,
  `IdempotencyKey`; после — `MarkApplied` (и, если заведём, дописать
  события-эффекты из `TurnResult`).
- Журналируются ходы, меняющие состояние (действия, `accuse`, `rest`, `present`).
  Свободные пробы/справки (`survey`, `facts`, `help`) в команд-лог не идут.
- Ключ идемпотентности: детерминированный из `(session_id, seq)` либо
  `(seed, turn, intent-hash)`.

Тесты: на ход в журнале появляется `pending` до и `applied` после; порядок
`Seq` совпадает с порядком ходов; несудимые команды не журналируются.

## Фаза 3 — Аудит-поток (в т.ч. --nl)

Тронуть `cli/`, `intent/`, `actor/` (передача данных наверх, без правки домена):
- На каждый ход писать `AuditEntry`: сырой ввод игрока; для `--nl` — интент от
  парсера и/или реплику актёра как `LLMProposal`; вердикт ядра (`refused`/класс
  исхода) как `CoreVerdict`; `Seq` = ссылка на команду.
- Правда реплея берёт **интент**, аудит — сырой текст. Проверить, что в команд-лог
  не попадает сырой `--nl` текст как источник.

Тесты: `--nl` пишет интент в команд-лог, сырой текст — в аудит; обычный режим
пишет команду без аудит-предложения LLM.

## Фаза 4 — Реплеер и версия ядра

Тронуть `cli/` (или новый `journal`/`replay` над `core`), `core`:
- `CoreVersion` — константа в домене (поднимается при изменении правил).
- Реплеер: `(дело + seed + журнал команд)` → состояние сессии; сверяет
  `CoreVersion` со `snapshot`-заголовком, при расхождении — явная ошибка.
- На старте: если журнал содержит хвост `pending` — реплеить его (восстановление
  после падения), идемпотентно.

Тесты: записанная сессия реплеится в идентичное состояние (обобщить
walkthrough-тест на журнал вместо `--script`); расхождение `CoreVersion` роняет
реплей; хвост `pending` реплеится один раз (идемпотентность).

---

## Фаза 5 — Проводка в cmd/dnd

Тронуть `cmd/dnd/main.go`:
- Флаг `--journal <файл>` — писать журнал сессии (команд + аудит).
- Режим реплея: `--replay <файл>` — прогнать журнал вместо интерактивного ввода
  (рядом с существующим `--script`), сверив `seed`/`CoreVersion`.

Тесты/проверка: записать живую сессию с `--journal`, затем `--replay` даёт тот же
вывод; `go test ./...` зелёный.
