## Инварианты (во всех фазах)

1. Состояние меняется только через `Apply` или `ProposeMutation`; иного пути нет.
2. Доверенный путь правил (`Resolution.Mutations` → `applyMutations`) не меняется
   и капабилити-гейтом не облагается.
3. Недоверенный вид не касается фактов дела, `party_knowledge`, токенов, `truth`,
   механики броска — конструктивно (нет такого вида) и через инвариант-гейт.
4. Граница домена: `ProposeMutation`/валидаторы в `core`; капабилити-гейт над
   доменом; `core` не импортирует `llm`. `e2e/architecture_test.go` зелёный.
5. `go test ./...` зелёный после каждой фазы.

## Фаза 1 — Расширить набор мутаций и стор канона

Тронуть `core/`, `store/`:
- `core` `MutationKind`: добавить `MutCanonAmbient` (и объявить `MutWorldEvent`
  как форму без обработчика). У `Mutation` добавить поле `Text string` для
  payload канона (числовым видам не мешает).
- `store`: стор ambient-канона — `map[canonKey]string`, ключ `(CaseID, topic)`;
  методы `Canon(case, topic) (string, bool)`, `PutCanon(case, topic, text)`.
  Если стор канона уже заведён работой по Мастеру — переиспользовать, не дублировать.

Тесты: put/get канона; ключ по `(case, topic)`; повтор возвращает то же.

## Фаза 2 — Валидируемый вход ProposeMutation

Тронуть `core/mutate.go`:
- `func (g *Game) ProposeMutation(m Mutation) (Applied, Refusal)` (типы результата
  — что применено / причина отказа):
  - `MutCanonAmbient`: топик не из пространства имён фактов дела; текст непуст;
    по занятому ключу — вернуть существующее (идемпотентно), при конфликте — отказ;
    иначе `PutCanon` и вернуть applied.
  - числовые виды на этом пути: **не принимаются** от недоверенного предложителя
    (они — прерогатива правил); отказ с причиной.
  - неизвестный вид → отказ (в отличие от `applyMutations`, который молчит).
- `applyMutations` (доверенный путь правил) не трогаем.

Тесты: `MutCanonAmbient` валидный → applied + канон записан; топик-как-факт-дела →
отказ; пустой текст → отказ; повтор ключа → идемпотентно; `MutHarm` через
`ProposeMutation` → отказ; неизвестный вид → отказ.

## Фаза 3 — Капабилити-гейт над доменом

Тронуть оркестратор (`cli`/`master`/новый тонкий слой над `core`):
- Функция-гейт: `(proposerRole, Mutation) → ok|refuse`, где допустимость вида
  берётся из капабилити-таблицы (`ProposeCanonAmbient` → `MutCanonAmbient`;
  `ProposeWorldMutation` → `MutWorldEvent`). Роль без нужного `Proposes` — отказ
  до вызова ядра.
- Порядок: капабилити-гейт (над доменом) → `core.ProposeMutation` (инвариант).
  Оба должны пройти.

Тесты: роль с `ProposeCanonAmbient` проводит канон; роль без него — отказ на
гейте, ядро не вызвано; роль не может провести числовой вид ни на гейте, ни в ядре.

## Фаза 4 — Инвариант «единственная граница»

Тронуть `e2e/architecture_test.go` (или соседний тест в пакете):
- проверить, что запись состояния идёт только через `Apply`/`ProposeMutation`:
  минимально — что мутирующие методы стора (`PutCanon`, тики часов, сдвиг
  диспозиции и т.п.) вызываются только из `core`, а слой над доменом ходит через
  `ProposeMutation`, а не в стор напрямую. Где полноценно проверить сложно —
  зафиксировать инвариант комментарием + точечным тестом на ключевые пути.

Тесты: попытка недоверенного слоя писать в стор мимо `ProposeMutation` не
компилируется/не проходит (по возможности), либо покрыта тестом на отсутствие
таких вызовов.
