# ADR-0004: Тонкий клиент, протокол turn-view и асс-стор как канон мира

**Статус:** Предложен
**Дата:** 2026-08-21
**Решает:** Валерий Ключников
**Связано:** `docs/adr/0001-layered-world-trusted-core.md` (слои, доверенное ядро,
API мутаций), `docs/adr/0002-action-log-write-ahead.md` (аудит генерации),
`docs/adr/0003-threat-model-free-dialogue.md` (недоверенный контент, аффордансы)

## Контекст

Игру нужно упаковать в мобильное приложение (iOS-first) с интерактивностью сверх
чата: тапабельные карты и перемещение, генерённые арты, карты и аватары. Вопрос —
как сделать клиент, не разрушив модель доверия из ADR-0001/0003, где сервер-ядро
авторитетно, а весь LLM-вывод недоверенный. Плюс: у команды есть наработки по
чатам на React Native (проект nomi), которые хочется переиспользовать.

## Решение

**Клиент — тонкий недоверенный презентационный слой над сервер-ядром.** Он
рендерит доверенный снепшот и шлёт интенты; каноном не владеет, правду не хранит,
исход не решает. Взломанный клиент может лишь послать команду, которую сервер
валидирует — та же поза, что у нарратора. Почти вся логика уже на сервере, значит
клиент тонкий по построению.

**Интерактив = объект, привязанный к интенту.** Каждый интерактивный элемент —
канонический объект с интентом: узел карты → `move_zone`, аватар NPC → `talk_to`,
предмет листа → `present`, проп → `examine`, часы HUD → инфо. Сервер отдаёт список
интерактивных объектов и интент каждого; клиент рисует их (чипы, хотспоты на арте,
строки листа) и по тапу шлёт **тот же типизированный интент**, что и свободный
текст. Одна модель — много рендеров; аффордансы из ADR-0003 — этот же список.

**Протокол turn-view** (типизированный, версионируемый) на каждый ход несёт:
блоки повествования (проза/реплики — контент в контейнерах, **не разметка**),
аффордансы с тегами проверок, HUD состояния, результат броска, **scene-visual**
(ссылка на арт), **map-view** (арт + хотспоты по `node_id` с флагами
достижим/известен), **participants** (аватар-ссылки). Всё — ссылки и
типизированные хотспоты, никогда не разметка и не навигация от модели.

**Ассеты — канон слоя мира, в сторе, а не в кэше.** Арт, карты, аватары —
персистентные адресуемые ассеты: генерятся раз, хранятся, шарятся между игроками,
переживают сессии. Кэш/CDN — доставка перед стором, источник правды — стор.
Добавление ассета = **мутация мира** через API мутаций (роль иллюстратора
предлагает из read-scope, никогда из `truth` → safety-классификатор → валидация →
стор → провенанс в аудит). **Immutable-по-ссылке:** регенерация даёт новую
версию/id, не перезапись — иначе в общем мире «то же лицо» разъедется у разных
людей.

**Карта: топология — данные, картинка — оверлей.** Граф локаций (`adjacent`) в
ядре; арт — декоративный бэкграунд; хотспоты привязаны к `node_id`. Что тапабельно
и куда идти — состояние ядра (`party_knowledge`/посещённое), не рисунок. Лишняя
деталь на арте без хотспота безвредна.

**Транспорт — два канала:** запрос-ответ на команды (интент → turn-view) и
стрим/пуш (потоковая проза токенами; события мира от других игроков). Под Go —
gRPC/Connect или REST для команд, WebSocket/SSE для стрима.

**Платформа — React Native, iOS-first.** Чат-стрим переиспользуем из nomi;
интерактивный слой (HUD, лист, тапабельная карта, кубик, аватары) — новый, под
него react-native-skia (canvas, жесты, анимации). Android — дорога открыта.

## Таксономия аватаров (сабрешение)

- **Именованные фигуры мира:** канонический персонаж, один аватар на `entity_id`,
  все видят то же лицо — узнаваемость и репутация между игроками.
- **Пул переиспользуемых лиц:** библиотека заранее сгенерённых лиц, назначается
  рандомным NPC детерминированно по (архетип, регион, хеш `entity_id`) и
  канонизируется — тот же NPC с тем же лицом, маржинальная цена ≈ 0.
- **Аватар игрока-героя:** сгенерён/кастомный, в сторе, персистентный.

## Рассмотренные варианты (платформа)

### React Native (принимается)

| Измерение | Оценка |
|---|---|
| Переиспользование | Высокое: чаты из nomi готовы |
| Интерактив/анимации | Хорошо через skia; не нативный максимум, но достаточно |
| Путь на Android | Открыт из коробки |
| Скорость до iOS | Высокая |

**За:** готовые наработки, один код, тонкий клиент минимизирует портируемую
логику. **Против:** «игровой» фид чуть ниже нативного; тяжёлая графика — через skia.

### SwiftUI (нативный)

**За:** максимум фида, хаптика, полировка. **Против:** новый стек для Go-шопа,
Android с нуля, наработки nomi не переиспользовать. Отклонён при iOS-first + RN-опыте.

### PWA в обёртке

**За:** быстрее всего на вебе. **Против:** трение App Store, слабый нативный фид и
хаптика, хуже интерактив. Отклонён.

## Последствия

- **Проще:** модель доверия тянется на клиент без исключений (тап = интент,
  проза/картинка — декорация); ассеты-в-сторе дают визуальную консистентность
  общего мира и экономят генерацию (раз на всех).
- **Сложнее:** новая роль иллюстратора + safety-классификатор + асс-стор с
  версионированием; протокол turn-view надо спроектировать и версионировать;
  интерактивный слой RN — новая работа поверх чатов nomi.
- **Пересмотреть:** источник интерактивных объектов (обобщить аффордансы до
  пространственных хотспотов); политику регенерации/версий ассетов; StoreKit-
  монетизацию и Apple-UGC-модерацию (смыкается с классификатором инъекций).

       не `truth`); генерация-как-мутация через API мутаций; провенанс в аудит.
5. [ ] **Таксономия аватаров:** именованные фигуры, пул с детерминированным
