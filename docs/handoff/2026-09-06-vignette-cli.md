# Хендофф: интерактивный CLI виньетки + оценка проекции в turn-view

**Дата:** 2026-09-06 · **Исполнитель:** локальный Claude Code · **Ветка:** поверх
`claude/core-dnd-mechanics-merge-b2e20d` (зависит от кода виньетки; на pivot ещё не влито).

## 0. Контекст

Виньеточный трек играется через сервер **в процессе** (`server.vignetteRuntime`,
проверено e2e), но **интерактивно его ничем не подать**: `cli/`/`tui/`/`client/` про
виньетку не знают, а её кадр (`vignetteView`: scene/surfaces/revealed/state_note/beat/
ended/end_text) — новая форма. Чтобы **сесть и поиграть, откалибровать и прогнать живой
Ф6**, нужен тонкий вход. Не WS-клиент, а **in-process CLI**, гоняющий ТОТ ЖЕ turn-путь,
что и сервер (как консоль прототипа `proto/`, но на доменном стеке).

## Задача A — интерактивный CLI виньетки (главное)

**Цель:** `go run ./cmd/vignette` даёт человеку играть виньеточную сцену по ходам в
терминале, задействуя ТОТ ЖЕ путь `Judge.Rule → State.Adjudicate → narrate(только
Revealed) → Guard.Check(+ended-карваут)`, что и `vignetteRuntime`. Офлайн по умолчанию,
богаче с ключом. Пишет прогон в JSONL для оценки/Ф6.

**Требования:**

1. **Переиспользовать, не форкать.** Пер-ходовая логика (судья → `Adjudicate` → нарратор
   получает ТОЛЬКО `res.Revealed` → страж с `allowed=[EndText]` на `ended`) должна быть
   ТЕМ ЖЕ кодом, что у `vignetteRuntime.narrateLocked`. Если надо — **вынеси шаг хода в
   экспортируемый хелпер** (напр. `server.VignetteTurn(...)` или пакет `vignette` с
   методом, не завязанным на broadcast), который зовут и рантайм, и CLI. **Не копипастить**
   логику нарратора/стража — иначе то, что мы «чувствуем» в CLI, разойдётся с сервером.
2. **Источник сцены.** Офлайн → встроенный/фикстурный `SceneSpec` (переиспользуй
   `cases/nightguest` или зашей пару спеков; выбор через `CASE`). С `OPENROUTER_API_KEY`
   + `THEME` → `scenegen.Generate(theme, mode)` → `Repair` → `Validate` → `vignette.FromSpec`
   (при сбое — фолбэк на встроенный, как в прототипе).
3. **Роли по наличию ключа — печатай три стартовые строки в stderr** (как прото), чтобы
   fake-прогон не спутать с живым: офлайн → `KeywordJudge` + fake/эхо-нарратор
   (`llm.NewFake`) + `KeywordGuard`; с ключом → LLM-судья + настоящий `master.Master` +
   LLM-страж. Явно указывай, кто активен.
4. **Петля (как консоль прото):** печать интро; на ход — читать stdin, показать строку
   броска если была, показать вывод Мастера (после стража) и `StateNote`; на `ended` —
   занавес. `:q`/`выход` — выход.
5. **Запись:** каждый прогон в `runs/*.jsonl` через СУЩЕСТВУЮЩИЙ `vignette/recorder.go`
   (с трейсом генератора, если генерилось) — чтобы оценивать офлайн и делать Ф6.
6. **Env — по конвенциям прото** (мышечная память): `OPENROUTER_API_KEY`, `MODEL`,
   `GUARD_MODEL`, `JUDGE_MODEL`, `GEN_MODEL`, `THEME`, `MODE`, `CASE`.

**Приёмка A:**
- Офлайн `go run ./cmd/vignette` (CASE=nightguest) играется до конца без ключа.
- `THEME="…" MODE=… OPENROUTER_API_KEY=… go run ./cmd/vignette` — генерит и играет.
- Пишется файл `runs/*.jsonl` (с gen-трейсом при генерации).
- CLI импортирует общий turn-путь сервера/виньетки, а не копию (проверить грепом, что
  narrate/guard-логика одна).
- `go test ./...` остаётся зелёным.

## Задача B — оценить проекцию виньетки в turn-view (развилка по клиенту; ТОЛЬКО оценка)

**Цель:** решить, сможет ли клиент рендерить виньетку **проекцией её состояния в
СУЩЕСТВУЮЩУЮ turn-view** (`view/` на сервере + `client/src/turnview`), или ей нужна своя
turn-view. **НЕ реализовывать** — прочитать обе схемы, наложить поля `vignetteView`
(scene/surfaces/revealed/state_note/beat/ended/end_text) на turn-view и отчитаться:
чистое соответствие / натужное / не влезает, с рекомендацией (переиспользовать-через-
проекцию vs своя turn-view у виньетки) и грубой оценкой объёма. Итог — короткий док в
`docs/handoff/`. Это развилка: от неё зависит, «клиент почти даром» или «клиенту нужна
отдельная вью».
