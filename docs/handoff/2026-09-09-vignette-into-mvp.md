# Хендофф: внедрить виньеточный движок в MVP как отдельный вид сессии

**Дата:** 2026-09-09 · **Исполнитель:** локальный Claude Code (есть Go 1.26.3, компилит и гоняет тесты) · **База:** ветка `claude/core-dnd-mechanics-merge-b2e20d` (виньеточный движок уже там; MVP — её предок, 0 коммитов расхождения).

## 0. Контекст и решения (не пересматривать без явного согласования)

Продукт — сингл-MVP: доверие к ИИ, набор каток, создание персонажа, реальный RN-клиент. На ветке `b2e20d` **уже общее** и портировать НЕ надо:

- **D&D-рулзы** — `core/ruleset.go` (`threshold` + `dnd5e`) и весь `rules/dnd5e/`. Идут через общий реестр ruleset'ов + `CreateWithRuleset`.
- **Архитектура агентов (анти-лик Мастер+Страж)** — уже дефолтный путь основного приключения: `cmd/server/narrator.go → buildNarrator()` собирает `master.New(gw)` и оборачивает `guard.New(gw)` (`GUARD_LINES=true`), нарратив через `RoleChatMaster` + `RoleCanonGuard`.

Значит net-new к внедрению — **только виньеточный движок** (`vignette/` — свой цикл: секрет-правда + тиры + пассивная перцепция; `server/vignette_runtime.go` + `server/vignette_manager.go`; `cmd/vignette` CLI).

**Решение владельца (2026-09-09):** виньетка входит в MVP **отдельным видом сессии**, НЕ как `RulesetKind`, вставленный в dnd5e-рантайм. Виньеточный цикл — другая игра (детектив/мистерия против «мерки по листу персонажа»), у неё свой рантайм и свой view. Продуктовая интеграция, не слияние движков. **Стража виньетки сохраняем** — это геймплей (держит тайну хоррор-загадки до развязки), а не только security; сингл-MVP снимает защиты от инъекций, но Страж виньетки остаётся.

**Генератор — часть ядра.** `scenegen/` — core-способность (тема → сцена), а не приложение к виньеточному треку. Виньетка — её первый потребитель через `vignette.FromSpec`. В интеграции позиционировать генератор как core-уровень (доступен из продуктового create-пути, не только из CLI); НЕ прятать его в виньеточный трек как приватную деталь.

ADR к соблюдению: **ADR-0009** (виньетка — серверный трек, M1a `rules/threshold` байт-в-байт нетронут), **ADR-0008** (Мастеру уходит ТОЛЬКО revealed), **ADR-0006** (плюрализм правило×сценарий).

## 1. Ветка

Отвести `claude/vignette-into-mvp` от `claude/core-dnd-mechanics-merge-b2e20d`. Это линейный потомок MVP (fast-forward-совместим), настоящего мержа/конфликтов нет. Вся работа ниже — на этой ветке. `go test ./...` держать зелёным на каждом шаге.

## Задача 1 — серверная продуктовая обвязка (вид сессии)

**Цель:** виньетка достижима из ТОГО ЖЕ продуктового потока, что и приключение (character-create → session-select → play), а не только из `cmd/vignette`.

1. **Discriminant вида.** Сессия несёт `kind: "adventure" | "vignette"`. Приключения → существующий `sessions`/`runtime` через `CreateWithRuleset`; виньетки → существующий `vignettes`/`vignetteRuntime` через `CreateVignetteFromCase`. Разводка по `kind` на входе создания сессии и в списке активных сессий (resume).
2. **Витрина.** `server/catalog.go`: добавить в `CaseSummary` поле `Kind string` (`adventure` по умолчанию для обратной совместимости; `vignette` для виньеточных дел, напр. `cases/nightguest`). `GET /cases` отдаёт `Kind`, чтобы клиент показал виньеточные сценарии в session-select и знал, каким путём их поднимать.
3. **Роутинг создания.** Выбор дела с `kind=vignette` в session-select → `CreateVignetteFromCase(caseName, seed, userID)`; `kind=adventure` → прежний `CreateWithRuleset`. Не ломать существующую совместимость персонаж↔ruleset для приключений.
4. **Генератор из продукта (core).** Обеспечить продуктовый путь «тема → `scenegen.Generate` → repair → validate → `CreateVignette(spec,…)`», а не только CLI-путь. Генератор зовётся как core-способность; виньетка — потребитель спека. (Клиентский UI генерации — вне рамок этого хендоффа; нужен серверный эндпоинт/путь, доступный продукту.)

## Задача 2 — починить два серверных бага виньетки

Оба нашёл фронтенд-агент, подтверждено чтением кода.

1. **Интро сцены не доезжает до клиента.** `server/vignette_manager.go` `CreateVignette` (~стр. 23) поднимает рантайм, но интро-прозу Мастера при создании не генерит: `snapshotFrameLocked` шлёт только `vignetteView` (scene/surfaces/revealed/state_note/beat/ended/end_text), без вступления. Игрок открывает сцену без интро.
   **Фикс:** при создании (или на первом attach/subscribe) сгенерировать интро ТЕМ ЖЕ путём, что ход — холодный вход (только поверхности, без перцепции) → `vignette.Narrate`/Мастер → Страж → бродкаст прозой в чат-канал. Как в консоли прото (`introInput := {SceneTitle, Surface: [Intro, …surfaces]}` → render → guard → печать). Не копипастить — переиспользовать общий turn-путь.
2. **Гонка порядка кадров.** `server/vignette_runtime.go` `applyInput` (~стр. 121): на ~стр. 151 бродкастит `OpSessionState{Ended: res.Ended, EndText: res.EndText}` РАНЬШЕ, чем ~стр. 161 `narrateLocked` шлёт финальную прозу Мастера. Клиент видит `session_state{ended:true}` и рисует занавес до развязки.
   **Фикс:** сначала нарратив финального хода (`narrateLocked`), ПОТОМ ended-кадр `OpSessionState`. Либо не выставлять `ended` в промежуточном `session_state` до отправки финальной прозы. Порядок кадров: [бросок?] → проза Мастера (после стража) → session_state{ended,end_text}.

**Тест на регресс:** добавить/расширить `server/vignette_e2e_test.go` — (a) после Create приходит интро-кадр прозой до первого ввода; (b) на завершающем ходу финальная проза приходит СТРОГО раньше `session_state{ended:true}`.

## Задача 3 — клиент: рендер виньетки по виду сессии

Фронтенд-агент оставил каркас (сейчас неотслеживаемыми файлами в рабочем дереве — усыновить или переписать под проверку компиляцией/тестами):

- `client/src/vignette/types.ts` — форма `vignetteView`.
- `client/src/net/vignetteNetSource.ts` — источник кадров виньетки (WS/in-proc).
- `client/src/vignette/useVignetteView.ts` — хук состояния виньетки из кадров.
- `client/src/net/socketToken.ts` — токен сокета.
- `client/src/screens/session/sessionKind.ts` (+ `__tests__/sessionKind.test.ts`) — discriminant вида на клиенте.
- `client/src/components/vignette/VignetteScreen.tsx` — экран виньетки (scene → surfaces → revealed → state_note → beat → занавес по ended+end_text).

**Требования:**
1. Session-select показывает виньеточные сценарии (по `Kind` из `GET /cases`) рядом с приключениями; выбор виньетки поднимает виньеточную сессию.
2. `SessionScreen`/роутер по `kind` рендерит: `adventure` → существующий turnview; `vignette` → `VignetteScreen`. Не втискивать `vignetteView` в turnview (Task-B вердикт `docs/handoff/2026-09-06-vignette-turnview-projection.md` — «своя тонкая вью»).
3. Интро показывается первым; занавес — только после финальной прозы (обратная сторона багфиксов 2.1/2.2).
4. Клиентские тесты (jest/RTL) зелёные; `sessionKind` покрыт.
